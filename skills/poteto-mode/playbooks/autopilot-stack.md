### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack the operator reviews and lands.** For "autopilot-stack", "stack them, don't ship", "build the stack, I'll land it". The sibling of **Autopilot-full**. The owner loop and the verification gate are the same; only the terminal differs. There a clean verdict authorizes the owner's merge. Here it appends a link to the one reviewed chain, and nothing auto-ships.

1. **Run the owner loop unchanged.** Use Autopilot-full step 2 for isolation, early decision and child trails, committed-head checks, code-ready reports, and fix-round merge bases. Parent publication remains bounded by the runtime contract. No owner receives merge authority.
2. **Audit hourly when authorized.** Use the hourly thread heartbeat and child reconciliation from Autopilot-full step 6. Append the queue table on every tick. Message only previously unreported tracked changes under Autopilot-full step 6. A replacement remains bounded to one retry and a repeated stall becomes a visible gap.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On her explicit go, create a goal with the full program objective. The goal continues across turns until the chain is done. On her stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** Apply Autopilot-full step 4 at code-ready and every later patch-changing push. Require independent gates, live behavior, and at least two focused review lanes. Audit receipts at STACK-READY. Batch every proven defect for fix-forward with red tests covering all matching sites or a repro receipt. Keep the stable merge base during fixes. Reuse lane results only under the shipping patch-id rule. Nothing enters the stack without a matching clean verdict.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** The parent owns stack membership, exact parent tips, and PR base/head configuration. Each child rebases onto its parent's exact tip and targets that parent branch. Use the supported built-in PR tool or resolved forge to create and retarget PRs. Graphite is optional when installed and applicable to this stack. Before any Graphite operation, inspect its local parentage and limit the operation to the intended membership. Owners report their tip and intended parent. Owners never submit, retarget, or force-push another owner's branch. Publication remains in the parent effect phase under the runtime contract.
7. **Absorb drift at the root, then re-verify what moved.** The parent owns topology and absorbs trunk drift through the supported stack tool. Owners resolve only their own conflicts. Record verdict head, base, and stable patch-id for each PR. Apply `playbooks/shipping.md` after every restack. Changed patches require fresh verification except lanes with proven identical build output under that rule. CI and mergeability always run at the current head. A new pinned value needs an authorized countersign; landed drift does not.
8. **Deliver the chain.** Return one linear bottom-to-top list with exact PR base/head pairs and a verifier verdict for every link. Show it through the resolved forge, or Graphite when selected. The operator reviews and lands the chain within the authority they granted. Nothing auto-ships.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
