### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator task: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own tools. Dispatch, wait on, steer, and cancel workers through the supported Codex subagent surfaces. Keep the program's state in one notes file and a decision trail per the **show-me-your-work** skill, beneath an operator-named state root or the repository's documented plan directory. Never infer a host-private store. Watch each PR through PR and CI event subscriptions when the runtime has them. Otherwise check live PR state at an authorized thread heartbeat. A multi-day program uses a durable goal and thread heartbeat only under the lifecycle authority the runtime contract requires. Call no orchestration scripts, never hold a shell open to sleep, and never relay messages or status between agents.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch, in its own worktree, and carries the PR from build to merge-ready. Only the owner rebases or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. Pushes, merges, and other external writes stay with you, the parent, unless the user explicitly assigned them to owners. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its brief carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Prove write isolation before dispatch with a separate worktree or exclusive paths, or run the work serially. Work that needs a live-control capability, a simulator, local-only auth, or this machine's task history stays on the surface that has it. Use a remote execution host only when one is available and within the user's authority. Pick each subagent's profile per the Subagents section.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and briefs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Use the nesting depth and capacity the runtime reports, and flatten the queue into the parent when nesting is unavailable. Keep about ten workers in flight per coordinator, within that capacity, and start the next one as each finishes instead of waiting on a whole batch.
- **Reuse a worker only when new work needs its built state,** such as its checkout, uncommitted changes, or a running process. Message a worker only for a follow-up on the same work. Never message one to check on it. Read supported live status instead, because a message restarts an idle agent.
- **Each PR gets a verifier that isn't its author,** on a different observable model family when one is available. Otherwise label the verifier's model inherited or unverified. A PR merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through brief, owner, verifier, and merge before you fan out, so a flaw in the brief costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each brief names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, the actions it must not take, and the fact that other actors may be editing the repository. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** A child report is evidence, not completion. Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's briefs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you dispatched as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its commits, pushes, and PR activity, not its status text. Cancellation is a request, not proof that writes stopped, so inspect its tree and partial output first. Retry once by cause, with a fresh consolidated brief: a smaller scope after a context or memory limit, the same brief after a dropped connection, and a different validated profile after a tool error. When the retry fails too, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
